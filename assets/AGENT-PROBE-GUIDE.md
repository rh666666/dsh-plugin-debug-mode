# 探针写法指南（生成给 Agent 的精简版）

> 本文件是 `dsh_debug_start` 响应里回给 Agent 的正文来源；模板变量由宿主替换。
> 目标是让 Agent 不必读插件的任何源码就知道该怎么埋点。

本次调试任务的固定信息：

- 任务哈希：`{{HASH}}`
- 日志文件（绝对路径）：`{{LOG_PATH}}`
- Node 探针桩（绝对路径）：`{{PROBE_STUB}}`
- Node 探针引入写法：`{{PROBE_IMPORT}}`
- 浏览器/远程探针桩（绝对路径）：`{{BROWSER_STUB}}`
- HTTP 摄入端点：`{{PROBE_ENDPOINT}}`
- 轮次：第 `{{ROUND}}` 轮
- 需求描述：{{GOAL}}

> `{{PROBE_IMPORT}}` 是宿主给出的**可直接 import 的说明符**（`file://` 形式，
> Windows 与 POSIX 都成立）。若你的工具链不接受 `file:` 说明符（部分打包器/`tsc` 配置
> 会挑食），把它换成本文件到探针桩的**相对路径**即可——桩就在任务目录的 `runtime/` 下。

---

## 零、你不要运行任何命令（**先读这一条**）

调试模式是宿主侧的一个**独立服务**。你在这个流程里的动作只有两种：

1. **给它发信号**：`dsh_debug_start` / `report` / `continue` / `read` / `end`；
2. **用编辑工具在源代码里埋点与改代码**。

**跑起来复现是用户的事，不是你的。** 不要为了调试去执行任何 shell 命令——
不需要 `npm run`、不需要起本地服务器、不需要 `node -v` 探路。
（`bash` / `pwsh` 在某些环境里会被策略整个挡掉，那**不影响**这条流程；
被挡了就**直接埋点交卷**，不要去找替代命令或替代路径。）

唯一需要"运行"的东西是为**没有文件系统的运行时**准备的那条 HTTP 通道，见 §五。

## 一、先分清四件事（**最容易混的一处**）

调试模式下你有四种动作，规则各不相同：

| 动作 | 能改行为吗 | 约束 |
| --- | --- | --- |
| **埋探针**（加日志） | **绝对不能** | 只加可观测性；见铁律 1 |
| **读日志** | —— | 只走 `dsh_debug_read`；见铁律 3 |
| **改代码**（修 / 探索） | **可以**（这正是目的） | 受 §三 的轮次约束；改动要能被单独撤销 |
| **临时探索块** | 可以，但**必须在收尾时消失** | 用 `dsh-debug:temp` 标记；见 §七.1 |

> 铁律 1 说的是**探针**不许改行为，**不是**说你不能改代码。
> 改代码是这个插件的正当行为之一——只是必须和探针分开记账（见 §三）。

## 二、铁律

1. **探针只加可观测性，不改行为。** 探针不得改变控制流、返回值、时序（不许引入
   sleep/await 抖动）、副作用或异常语义。你是在给代码装仪表，不是在改代码。
2. **每一处探针必须能被机器摘除。** 用「探针块」包裹，标记前缀固定为
   `dsh-debug:probe`（见下）。结束调试时宿主会按这个标记逐处删除；标记之外的
   任何东西都不属于本次任务。
3. **不许自己找日志文件。** 日志内容一律通过 `dsh_debug_read` 获取；
   不要 `cat`/`read` 日志文件（会浪费上下文，而且拿不到宿主的分组计数与增量摘要）。
4. **先埋点，再让用户复现。** 埋完立刻调用 `dsh_debug_report` 汇报埋点清单，
   然后停手等用户复现；不要在同一轮里既埋点又猜结论。
   **交卷时务必给面板两样东西**——你交卷之后，用户唯一能看到的就是它们：
   - `headline`：一句话结论（≤ 80 字）。用户在输入框上方那张卡片上读到的就是这一句，
     不要把整篇分析倒进去（宿主会截断，而截断的半句话比没有更糟）。
   - `reproSteps`：**让用户照着做的复现步骤**，一条一个可执行动作。
     反例：「请复现一下」「看看还会不会」——那不是步骤，是愿望。
     正例：「打开保存对话框」「清空标题后点保存」「回到列表页」。
     面板会渲染成编号清单，所以每条都要能独立执行、不要写"同上"这类指代。
5. **覆盖假设，而不是撒网。** 每处探针要能证实/证伪一个具体假设；
   在 `report` 的 `probes` 里逐条说明「这处探针是为了验证什么」——
   宿主会用这份清单**点名"计数为 0"的探针**，那是整份日志里最贵的信号。
6. **深挖优先于铺开。** 优先在数据流入/流出的边界、状态变更点、分支判定点、
   异步回调边界埋点；不要在每个函数入口无脑打一行。

## 三、什么时候可以改代码

### 3.1 第 1 轮：只取证，不改代码

第 1 轮默认**不改任何代码**，只埋探针。原因不是保守，而是**先改代码会掩盖现场**：
在没看到数据之前猜的修法一旦改掉原始行为，后面的日志就再也证不出真相了。

闸门是**机器判定的**，而且判据很窄：第 1 轮只要出现 `dsh-debug:change` 标记、
或者你在 `changedFiles` 里报了文件，宿主就拒绝这次交卷。
**埋探针本身不算改代码**——那是在改文件，但不是改行为，宿主分得清这两件事。

### 3.2 第 2 轮及以后：允许先改代码再验

后续轮次你已经有真实日志在手，**允许先按假设改代码，再埋点验证**：

- 改完必须**再埋点**，用日志证明「改之前复现、改之后不复现」，
  或者证明「现象变了」从而缩小范围；
- 不要改完就宣布修好了——那又回到猜。

### 3.3 改动的记账纪律（**必须**）

- 每处改动用 `dsh-debug:change {{HASH}} 说明` 标出来（同一行或紧邻的上一行）；
- 每个改过的文件都必须出现在 `dsh_debug_report` 的 `changedFiles` 里；
- 结束调试时，**只撤探针，不撤你的修复**：在回复里逐条列出
  「哪些是修复（保留）」「哪些是探针（已删）」「哪些是临时探索改动（已还原）」。
- ⚠️ 用 `git diff` / `git checkout` 之类手段撤销时，**绝不要**把用户本来要求的
  修复一起 revert 掉。

### 3.4 宿主也在看（工作区 diff）

从进入调试模式起，宿主会**自己**在工作区建索引，并在你每次交卷时 diff 一遍：

- **新增文件**会被逐个点名（真检测，不靠你自报）；
- **被改动的文件**会与你的 `changedFiles` 对账。你漏报的，宿主会按"行为改动"
  替你记进**修复账**——收尾时**不会**回滚它们，所以漏报不会误删你的工作，
  但会让你给出的清单看起来不可信；
- 既没有探针块、也没有 `dsh-debug:change` 标记的改动，用户**无从分辨**它是修复
  还是探针。补一行标记，比事后解释便宜得多。

## 四、如果这个 bug 一眼就能看出根因

`/debug` 是用户发起的，但**你不必照做**。读完代码后如果根因明确（空指针、明显的
拼写错误、缺一次 await、写死的常量……），就：

1. **不要**调用 `dsh_debug_start`；
2. 直接告诉用户：这个问题不需要调试模式，说明根因，并**直接改代码**；
3. 改完给出验证方式。

票据会自己过期失效，用户下次想调试时重新 `/debug` 即可——你不需要为「拒绝了」
做任何清理动作。

代价对比很清楚：一次 `/debug` 要用户复现、要埋点、要读日志；一眼能看出的问题
直接修完更省用户的时间。**不要为了走流程而走流程。**

## 五、没有文件系统的运行时（浏览器页面 / 远端进程）

Node 桩靠 `node:fs` 直接写日志。**浏览器里的页面没有文件系统**，而且：

- 页面里的 `<script>` 不能 `import` 一个 `file://` 模块（CORS 会拦掉 module）；
- 就算能加载，`appendFileSync` 在浏览器里也不存在。

所以宿主额外开了一条**只追加写**的摄入端点，并生成了一个浏览器探针桩：

- 桩文件：`{{BROWSER_STUB}}`（经典脚本，不是 module）
- 摄入端点：`{{PROBE_ENDPOINT}}`
- 记录格式与 §七 的探针块里那些调用完全一致；桩只负责**传输**，落盘由宿主用同一行协议完成

用法（把两行都放进**探针块**里）：

```html
<!-- dsh-debug:probe {{HASH}} start -->
<script src=".dsh/debug-mode/tasks/{{HASH}}/runtime/probe.browser.js"></script>
<!-- dsh-debug:probe {{HASH}} end -->
```

然后在可疑位置调用全局函数 `dshProbe`（同样夹在探针块里）：

```html
<script>
// dsh-debug:probe {{HASH}} start
dshProbe('buggy-demo.html:42:onclick', { itm: typeof itm, list: todos.length })
// dsh-debug:probe {{HASH}} end
</script>
```

约束与注意：

- 经典 `<script src>` 在 `file://` 下是同源加载，**不需要起本地服务器**；
  若页面有 CSP 挡了它，就把桩文件的内容整段粘进一个探针块里（同样是经典脚本）。
- 记录是**批量发送**的（约 200 ms 一批，并在页面隐藏/卸载时冲刷）——
  "用户复现完就关页面"那一刻的现场不会丢。
- 投递是**尽力而为**：页面发得出去就落盘，发不出去就静默丢弃（探针永远不许把页面搞挂）。
  所以 `read` 为空时，先怀疑投递，再怀疑埋点位置。
- 端点只接受**本任务哈希**的记录，字段由宿主重新序列化（`task` 由宿主写死，投递方说了不算），
  单行 8 KiB、总量 16 MiB 与 Node 桩同一套限额。
- Python / 其它语言进程同理：按 §六 的行协议，`POST {{PROBE_ENDPOINT}}`
  一个 NDJSON 纯文本体（`Content-Type: text/plain`）即可，**不需要**宿主再写一个桩。
  单条对象、对象数组、NDJSON 三种形态都收。

## 六、Python 与其他自带运行时的语言

宿主的默认桩是 Node/JS 版；**Python（或其它语言）项目由 Agent 按同一行协议自写桩**：

- 落点：`{{TASK_DIR}}/runtime/probe.py`
- 协议：一行一条 JSON，字段顺序 `ts, task, probe, level, msg, data`，
  与 `lib/protocol.js` 一致；`ts` 为本地时间 ISO-8601（毫秒）。
- 铁律：`try/except` 全包、失败安静降级、`open(path, "a")` 追加写并立即 close、
  单行 ≤ 8 KiB、总量 ≤ 16 MiB（到顶后写一条 `probe: "debug-mode:overflow"` 就停手）。
- 埋点同样用探针块包裹（Python 注释形式）。
- **另一种更省事的选择**：进程能发 HTTP 就用 §五 的摄入端点——
  `POST {{PROBE_ENDPOINT}}`，体是 NDJSON 纯文本，不必自己处理文件与并发。

## 七、探针块写法（**三色标记**）

标记决定"收尾时怎么处理"，所以颜色不能混：

| 标记 | 含义 | 收尾动作 |
| --- | --- | --- |
| `dsh-debug:probe {{HASH}} start/end` | 探针 | **必删** |
| `dsh-debug:temp {{HASH}} start/end` | 临时探索（例如一段临时代码、一个 dump） | **必删** |
| `dsh-debug:fix {{HASH}} 说明` | 修复 | **永久保留** |
| `dsh-debug:change {{HASH}} 说明` | 行为改动（修复的备注） | **永久保留** |

`fix` 与 `change` 是**单行**标记，不需要 `start/end`；`probe` 与 `temp` 必须成对，
且**成对的两个标记缩进必须一致**、中间不许夹别的标记行——不满足这三条的区间宿主
**不会自动删**，而是丢进"隔离区"请用户逐条决定（宁可脏关闭，不可自动删用户代码）。

TypeScript / JavaScript：

```ts
// dsh-debug:probe {{HASH}} start
import { probe } from '{{PROBE_IMPORT}}'
probe('src/order/service.ts:118:resolve-total', { orderId, items, total })
// dsh-debug:probe {{HASH}} end
```

若文件已有 import 区，把 `import` 合并进原 import 区、只把**调用**留在探针块里，
同样用 `start`/`end` 夹住调用行。

Python：

```python
# dsh-debug:probe {{HASH}} start
from dsh_probe import probe
probe("app/order/service.py:118:resolve-total", {"order_id": order_id, "total": total})
# dsh-debug:probe {{HASH}} end
```

### 7.1 临时探索块（第 2 轮起才会用到）

临时改一段代码来看现象、事后必须还原的，用 `temp` 而不是 `change`：

```ts
// dsh-debug:temp {{HASH}} start  —— 强制走缓存分支看现象，看完要还原
if (true) return cached
// dsh-debug:temp {{HASH}} end
```

## 八、改动块写法（第 2 轮起才会用到）

改代码时**不要**用 `dsh-debug:probe` 标记（那会让收尾时把修复也一起删掉）。
用 `dsh-debug:change` 单独标出来：

```ts
// dsh-debug:change {{HASH}} 修复：items 为空时 total 应为 0 而不是 null
const total = items.length === 0 ? 0 : items.reduce((sum, i) => sum + i.price, 0)
```

顺序有讲究：**修复在标记里，验证它的探针在探针块里**，两者相邻但不混：

```ts
// dsh-debug:change {{HASH}} 修复：空数组时返回 0
const total = items.length === 0 ? 0 : sum(items)
// dsh-debug:probe {{HASH}} start
probe('src/cart/total.ts:42:after-fix', { items: items.length, total })
// dsh-debug:probe {{HASH}} end
```

## 九、探针标识规范

`<仓库相对路径>:<行号>:<短标签>`，例如 `src/order/service.ts:118:resolve-total`。
同一个假设的多处观测点用同一短标签 + 不同后缀（`:before` / `:after` / `:catch`），
方便读日志时按标签串起来。

## 十、建议的观测点

| 位置 | 记什么 |
| --- | --- |
| 函数入口（关键路径） | 入参的**形状与关键值**（别整对象 dump，挑字段） |
| 分支判定前 | 参与判定的全部变量、走了哪个分支 |
| 状态写入/更新处 | 旧值、新值、触发来源 |
| 异步边界（请求/回调/事件） | 关联 id（requestId/traceId）、耗时、返回摘要 |
| 异常与降级路径 | 完整 Error（name/message/stack）、上下文快照 |
| 退出/清理 | 是否走到、资源状态 |

## 十一、一轮怎么走完（**顺序不能反**）

用户反馈「复现」之后，这一轮的日志**还在**——它就是你要的证据。按这个顺序走：

1. **`dsh_debug_read`** —— 先看现场。用户刚复现出来的东西全在这里，
   而它**只会存在到你想开下一轮为止**。
2. 分析：哪条假设被证实/证伪了，下一步换什么假设。
3. **`dsh_debug_continue`** —— 只有到这一步才**清空**日志、轮次 +1（哈希不变）。
   宿主会检查日志里还有没有你没读过的字节：有就拒绝清空，让你先读。
4. （第 2 轮起可以）改代码 → 补新探针 → 再 `dsh_debug_report` 交卷。

> ⚠️ **不要先 `continue` 再 `read`。** 早先的指南就是这么写的（`continue` 清空 → 读日志），
> 结果用户一点「问题复现」，现场当场消失——清空必须发生在**下一次用户复现之前**，
> 而不是用户刚复现完的那一刻。

用户选择「问题已解决」后：

1. 调用 `dsh_debug_end`（`summary` 必填：写给用户看的结论）；
2. 宿主按 `dsh-debug:probe {{HASH}}` 与 `dsh-debug:temp {{HASH}}` 标记摘除
   本次任务的全部探针与临时块（**先备份，绝不自动还原**），删除任务目录；
3. 在回复里逐条列出「修复（保留）/ 探针（已删）/ 临时探索改动（已还原）」。
- **收尾可能被暂停一次**：如果扫描发现"既不是本任务的探针、也不能确认是修复"的
  残留（陌生 hash、残缺标记、配对有歧义），宿主会拒绝关闭任务并把清单交还给你。
  这时用 `ask_user_question` **逐条**问用户三选一，然后把决定回填进
  `dsh_debug_end` 的 `quarantine` 参数再调用一次：
  `keep`（保留）/ `delete`（删除，先给用户看 diff）/ `mine`（用户自己处理）。
  这是硬规则：**不允许静默保留**——漏删的临时改动不报错、不告警，只是慢慢烂掉。

## 十二、上限（宿主会强制）

| 项 | 上限 | 超限行为 |
| --- | --- | --- |
| 单条日志行 | 8 KiB | 截断并标 `truncated` |
| 单任务日志总量 | 16 MiB | 写端停止追加，并写一条 `probe:"debug-mode:overflow"` |
| `dsh_debug_read` 返回行数 | 200（默认） | 显式声明省略量；warn/error **不受它影响** |

到顶之后不要再补探针——先收窄埋点，或者 `dsh_debug_continue` 清空日志再来一轮。
