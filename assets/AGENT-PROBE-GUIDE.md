# 探针写法指南（生成给 Agent 的精简版）

> 本文件是 `dsh_debug_start` 响应里回给 Agent 的正文来源；模板变量由宿主替换。
> 目标是让 Agent 不必读插件的任何源码就知道该怎么埋点。

本次调试任务的固定信息：

- 任务哈希：`{{HASH}}`
- 日志文件（绝对路径）：`{{LOG_PATH}}`
- 探针运行时（绝对路径）：`{{PROBE_STUB}}`
- 探针引入写法：`{{PROBE_IMPORT}}`
- 轮次：第 `{{ROUND}}` 轮
- 需求描述：{{GOAL}}

## 一、先分清三件事（**最容易混的一处**）

调试模式下你有三种动作，规则各不相同：

| 动作 | 能改行为吗 | 约束 |
| --- | --- | --- |
| **埋探针**（加日志） | **绝对不能** | 只加可观测性；见铁律 1 |
| **读日志** | —— | 只走 `dsh_debug_read`；见铁律 3 |
| **改代码**（修 / 探索） | **可以**（这正是目的） | 受 §三 的轮次约束；改动要能被单独撤销 |

> 铁律 1 说的是**探针**不许改行为，**不是**说你不能改代码。
> 改代码是这个插件的正当行为之一——只是必须和探针分开记账（见 §三）。

## 二、铁律

1. **探针只加可观测性，不改行为。** 探针不得改变控制流、返回值、时序（不许引入
   sleep/await 抖动）、副作用或异常语义。你是在给代码装仪表，不是在改代码。
2. **每一处探针必须能被机器摘除。** 用「探针块」包裹，标记前缀固定为
   `dsh-debug:probe`（见下）。结束调试时你会按这个标记逐处删除；标记之外的
   任何东西都不属于本次任务。
3. **不许自己找日志文件。** 日志内容一律通过 `dsh_debug_read` 获取；
   不要 `cat`/`read` 日志文件（会浪费上下文，且拿不到宿主的分组与增量摘要）。
4. **先埋点，再让用户复现。** 埋完立刻调用 `dsh_debug_report` 汇报埋点清单，
   然后停手等用户复现；不要在同一轮里既埋点又猜结论。
5. **覆盖假设，而不是撒网。** 每处探针要能证实/证伪一个具体假设；
   在 `report` 里逐条说明「这处探针是为了验证什么」。
6. **深挖优先于铺开。** 优先在数据流入/流出的边界、状态变更点、分支判定点、
   异步回调边界埋点；不要在每个函数入口无脑打一行。

## 三、什么时候可以改代码

### 3.1 第 1 轮：只取证，不改代码

第 1 轮默认**不改任何代码**，只埋探针。原因不是保守，而是**先改代码会掩盖现场**：
在没看到数据之前猜的修法一旦改掉原始行为，后面的日志就再也证不出真相了。

### 3.2 第 2 轮及以后：允许先改代码再验

后续轮次你已经有真实日志在手，**允许先按假设改代码，再埋点验证**：

- 改完必须**再埋点**，用日志证明「改之前复现、改之后不复现」，
  或者证明「现象变了」从而缩小范围；
- 不要改完就宣布修好了——那又回到猜。

### 3.3 改动的记账纪律（**必须**）

- 每处改动用 `dsh-debug:change:` 备注块标出来（第一行写清「改了什么、为什么」）；
- 每个改过的文件都必须出现在 `dsh_debug_report` 的 `changedFiles` 里；
- 结束调试时，**只撤探针，不撤用户的修复**：在回复里逐条列出
  「哪些是修复（保留）」「哪些是探针（已删）」「哪些是临时探索改动（已还原）」。
- ⚠️ 用 `git diff` / `git checkout` 之类手段撤销时，**绝不要**把用户本来要求的
  修复一起 revert 掉。

## 四、如果这个 bug 一眼就能看出根因

`/debug` 是用户发起的，但**你不必照做**。读完代码后如果根因明确（空指针、明显的
拼写错误、缺一次 await、写死的常量……），就：

1. **不要**调用 `dsh_debug_start`；
2. 直接告诉用户：这个问题不需要调试模式，说明根因，并**直接改代码**；
3. 改完给出验证方式。

票据会自己过期失效，用户下次想调试时重新 `/debug` 即可——你不需要为「拒绝了」
做任何清理动作。

代价对比很清楚：一次 `/debug` 要用户复现、要埋点、要读日志；一眼能看出的问题
直接修完更省用户的时间。**不要为了走流程而走流程。**

## 五、Python 项目

宿主的默认桩是 Node/JS 版；**Python（或其它语言）项目由 Agent 按同一行协议自写桩**：

- 落点：`{{TASK_DIR}}/runtime/probe.py`
- 协议：一行一条 JSON，字段顺序 `ts, task, probe, level, msg, data`，
  与 `lib/protocol.js` 一致；`ts` 为本地时间 ISO-8601（毫秒）。
- 铁律：`try/except` 全包、失败安静降级、`open(path, "a")` 追加写并立即 close、
  单行 ≤ 8 KiB。
- 埋点同样用探针块包裹（Python 注释形式）。

## 六、探针块写法

TypeScript / JavaScript：

```ts
// dsh-debug:probe {{HASH}} start
import { probe } from '{{PROBE_IMPORT}}'
probe('src/order/service.ts:118:resolve-total', { orderId, items, total })
// dsh-debug:probe {{HASH}} end
```

若文件已有 import 区，把 `import` 合并进原 import 区、只把**调用**留在探针块里，
同样用 `start`/`end` 夹住调用行。

Python：

```python
# dsh-debug:probe {{HASH}} start
from dsh_probe import probe
probe("app/order/service.py:118:resolve-total", {"order_id": order_id, "total": total})
# dsh-debug:probe {{HASH}} end
```

## 七、改动块写法（第 2 轮起才会用到）

改代码时**不要**用 `dsh-debug:probe` 标记（那会让收尾时把修复也一起删掉）。
用 `dsh-debug:change:` 单独标出来：

```ts
// dsh-debug:change {{HASH}} 修复：items 为空时 total 应为 0 而不是 null
const total = items.length === 0 ? 0 : items.reduce((sum, i) => sum + i.price, 0)
```

顺序有讲究：**修复在标记里，验证它的探针在探针块里**，两者相邻但不混：

```ts
// dsh-debug:change {{HASH}} 修复：空数组时返回 0
const total = items.length === 0 ? 0 : sum(items)
// dsh-debug:probe {{HASH}} start
probe('src/cart/total.ts:42:after-fix', { items: items.length, total })
// dsh-debug:probe {{HASH}} end
```

## 八、探针标识规范

`<仓库相对路径>:<行号>:<短标签>`，例如 `src/order/service.ts:118:resolve-total`。
同一个假设的多处观测点用同一短标签 + 不同后缀（`:before` / `:after` / `:catch`），
方便读日志时按标签串起来。

## 九、建议的观测点

| 位置 | 记什么 |
| --- | --- |
| 函数入口（关键路径） | 入参的**形状与关键值**（别整对象 dump，挑字段） |
| 分支判定前 | 参与判定的全部变量、走了哪个分支 |
| 状态写入/更新处 | 旧值、新值、触发来源 |
| 异步边界（请求/回调/事件） | 关联 id（requestId/traceId）、耗时、返回摘要 |
| 异常与降级路径 | 完整 Error（name/message/stack）、上下文快照 |
| 退出/清理 | 是否走到、资源状态 |

## 十、收尾

- 用户反馈「复现」后：`dsh_debug_continue`（清空旧日志，哈希不变）→ 读日志 →
  （第 2 轮起可以）改代码 → 再埋点 → 再 `report`。
- 用户选择「问题已解决」后：
  1. 按 `dsh-debug:probe {{HASH}}` 标记删除**本次任务的全部**探针块；
  2. 删除探针桩与任务目录；
  3. 用 `dsh_debug_end` 报告清理结果，并逐条列出
     「修复（保留）/ 探针（已删）/ 临时改动（已还原）」。
